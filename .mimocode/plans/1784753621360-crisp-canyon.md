# Plano de Migração: unipar-dashboard Web → Mobile

## Visão Geral

Transformar o sistema web **unipar-dashboard** (Next.js 16 + React 19 + Supabase) em um aplicativo mobile profissional (Android + iOS), reaproveitando o máximo de código existente.

## 2. ESCOLHA DA STACK MOBILE

### Comparativo decisivo

| Critério | Expo (escolhido) | React Native CLI | Capacitor |
|----------|:---:|:---:|:---:|
| Setup inicial | 1cmd | manual (dias) | depends on web |
| OTA Updates | EAS Update (built-in) | CodePush (3rd party) | Capgo (3rd party) |
| Expo Router | file-based (igual Next.js) | React Navigation manual | N/A |
| NativeWind | suporte oficial v4 | funciona mas manual | funciona |
| Push Notifications | expo-notifications | react-native-push-notification | Capacitor Push |
| Build & Submit | EAS Build (cloud) | local (Xcode/Android Studio) | local |
| Comunidade 2025 | maior生态 | encolhendo | nicho |
| Hot reload | Expo Go (instantâneo) | dev client (setup) | live reload |
| Deep linking | expo-linking (built-in) | react-native-linking | Capacitor |
| Manutenção | Meta + Expo | Meta only | community |

### Por que Expo vence para ESTE projeto

1. **Já existe scaffold em `mobile/`** com Expo 57 — não começa do zero
2. **Expo Router** segue o mesmo padrão file-based do App Router do Next.js — familiaridade imediata
3. **EAS Build** elimina a necessidade de Xcode/Android Studio para CI/CD
4. **NativeWind 4** já está configurado no scaffold — reaproveita o mental model do Tailwind
5. **expo-secure-store** já integrado para tokens (vs AsyncStorage genérico)
6. **OTA Updates** permite推送 correções sem passar pela Play Store/App Store

### Stack final escolhida

```
Expo 57 + Expo Router (file-based navigation)
React Native 0.86
NativeWind 4 (Tailwind para RN)
Zustand (state management — substitui Context API)
TanStack Query (server state — substitui polling manual)
Supabase JS SDK (auth + database + realtime)
expo-secure-store (tokens)
expo-notifications (push notifications)
expo-file-system + expo-media-library (uploads/downloads)
react-native-reanimated + react-native-gesture-handler (animações)
LiveKit React Native SDK (áudio/vídeo)
```

## 3. POR QUE ZUSTAND + TANSTACK QUERY

### Zustand vs Context API

O projeto atual usa 10 React Context stores. No mobile, Zustand é superior:

| Aspecto | Context API (atual) | Zustand (proposto) |
|---------|---------------------|---------------------|
| Re-renderizações | Toda mudança re-renderiza consumers | Seleção granular por selector |
| Boilerplate | Provider + Context + useContext = 3 camadas | 1 store = 1 arquivo |
| DevTools | Não tem | Redux DevTools integration |
| Persistência | Não tem | zustand/middleware (persist) |
| Code splitting | Difícil | Stores independentes |

### TanStack Query vs Polling manual

O projeto atual faz polling manual em todos os stores (8s-60s intervals). TanStack Query:

- Cache automático com stale-while-revalidate
- Background refetching
- Retry com backoff exponencial
- DevTools para debug
- **Elimina 90% do código de polling dos stores atuais**

| Sheet | `@gorhom/bottom-sheet` | Gesture nativo |
| Select | Picker custom ou bottom sheet | iOS/Android patterns |
| Tabs | Expo Router Tabs | Nativo do framework |
| Sidebar | Drawer (react-native-drawer) | Não usado no mobile |
| Card | `<View>` + NativeWind classes | Direto |
| Badge | `<View>` + NativeWind | Direto |
| Avatar | `<Image>` + fallback circle | Direto |
| Toast | `react-native-toast-message` ou sonner fork | Alternativa nativa |
| Tooltip | Long press + popover | Padrão mobile |
| Table | ScrollView + FlatList | Virtualizado |
| Form | React Hook Form + Zod | Mesma lib |
| Calendar | react-native-calendars | Nativo |
| Chart | victory-native ou react-native-gifted-charts | Alternativa Recharts |
| Tooltip | N/A | Long press nativo |
| ScrollArea | ScrollView/FlatList nativo | Não necessário |
| Skeleton | `<View>` + LinearGradient shimmer | Custom |
| Dropdown Menu | ActionSheet ou bottom sheet | Padrão iOS/Android |
| Command | N/A (não faz sentido mobile) | — |

### Componentes que precisam ser reescritos (0% reaproveitamento)

- **Sidebar** → Não existe no mobile (usa tab bar + stack navigation)
- **Todas as animações Framer Motion** → Reanimated (react-native-reanimated)
- **Drag and Drop (dnd-kit)** → react-native-draggable-flatlist
- **Gráficos Recharts** → victory-native ou react-native-gifted-charts
- **Toasts Sonner** → react-native-toast-message

### Componentes que podem ser adaptados (tipos lógica reutilizável)

- **Todos os componentes de feature** (TicketsPage, KanbanPage, etc.) → A lógica React é reutilizável, apenas os elementos HTML (`<div>`, `<span>`) viram `<View>`, `<Text>`
- **Filtros, paginação, search** → Mesma lógica, UI nativa

### Componentes que são 100% reaproveitáveis (puro TypeScript)

- **Schemas Zod** → `packages/shared/validation/`
- **Types** → `packages/shared/types/`
- **Utils** → `packages/shared/utils/`

### Exemplo de store Zustand

```typescript
// stores/tickets.ts
import { create } from 'zustand'
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query'

interface TicketsState {
  selectedTicketId: string | null
  setSelectedTicket: (id: string | null) => void
}

export const useTicketsStore = create<TicketsState>((set) => ({
  selectedTicketId: null,
  setSelectedTicket: (id) => set({ selectedTicketId: id }),
}))

// Hook de dados (TanStack Query)
export function useTickets() {
  return useQuery({
    queryKey: ['tickets'],
    queryFn: fetchTickets, // de packages/api/
    refetchInterval: 20_000, // fallback polling
  })
}
```

## 8. ARMAZENAMENTO

| Dado | Solução | Justificativa |
|------|---------|---------------|
| Tokens (access/refresh) | `expo-secure-store` | Criptografado no Keychain (iOS) / Keystore (Android) |
| Sessão Supabase | `expo-secure-store` (via Supabase adapter) | Auto-refresh integrado |
| Cache de dados | TanStack Query cache | In-memory + stale-while-revalidate |
| Dados offline | MMKV (opcional, fase futura) | 30x mais rápido que AsyncStorage |
| Preferências do usuário | `expo-secure-store` | Tema, notificações, etc. |
| Downloads (PDFs, anexos) | `expo-file-system` + `expo-media-library` | Armazenamento local |

## 13. RISCOS GLOBAIS

| Risco | Impacto | Mitigação |
|-------|---------|-----------|
| LiveKit RN SDK instável | Alto | Testar early na Fase 8; fallback para WebRTC nativo |
| NativeWind v4 bugs | Médio | Usar apenas classes estáveis; fallback para StyleSheet |
| Performance em devices baixos | Médio | FlashList + memo + lazy loading desde cima |
| Divergência Web ↔ Mobile | Alto | packages/shared/ garante single source of truth |
| Build Apple complexo | Baixo | EAS Build simplifica; Expo cuida do toolchain |
| Supabase Realtime no mobile | Médio | Dual-channel (WebSocket + polling) já implementado no web |

## 14. CRITÉRIOS DE SUCESSO

1. **Paridade funcional** — Todas as features do web disponíveis no mobile
2. **Performance** — App carrega em <2s, scroll 60fps, sem jank
3. **Código compartilhado** — >40% do código de negócio reutilizado
4. **Zero duplicação** — Types, constants, validation, utils em packages/shared/
5. **Build funcional** — APK (Android) e IPA (iOS) gerados com sucesso
6. **Push notifications** — Funcionando em ambos os platforms
7. **Deep linking** — Todos os links internos funcionam
8. **Offline resilience** — Dados em cache acessíveis sem internet
